# Product requirements

A small business needs one shared workspace to track projects, task owners, deadlines, and delivery progress. This test is a local single-workspace application using fictitious data. It is not a public multi-tenant service.

## Required outcomes
- R1: Create and list projects with name (1–100 trimmed characters) and optional description (maximum 1000). Project names need not be unique. IDs are generated by the server.
- R2: Create tasks belonging to an existing project. Fields: title (1–200 trimmed characters), owner (0–100), due_date (optional ISO YYYY-MM-DD valid calendar date), status (todo/in_progress/done). Default status is todo.
- R3: Edit task title, owner, due date, and status without changing its project. Delete a task with confirmation in the UI. Unknown IDs return 404; invalid inputs return 400. Empty PATCH returns 400. JSON null is allowed only for clearing due_date.
- R4: Filter tasks by project and/or exact status, combining both filters. Invalid status filters return 400. Unknown project filter IDs return 404. No matching tasks returns an empty list.
- R5: Show per-project total, completed, and overdue task counts. Overdue means due_date earlier than today's UTC date and status is not done. Due today is not overdue. The server computes these counts.
- R6: Persist projects and tasks in SQLite across restarts. Use foreign keys, parameterized SQL, transactions, and explicit ordering by created_at then id. Do not ship a seeded production database.
- R7: Provide a responsive business-friendly web interface to create projects, add/edit/delete tasks, filter by status, and view project summaries. Show loading, empty, validation, and network-error states. Labels and keyboard focus must be accessible. Render user data as text, never raw HTML.
- R8: Provide GET /health with service status. Bind to 127.0.0.1 by default; configurable host, port, and database path through environment variables. No external services or API credentials required at application runtime.

## Boundaries
No authentication, notifications, file upload, billing, team invitations, or external integrations in this dry-run application. State the local trusted-user scope clearly. No claims of public production readiness. No application deployment is requested.
